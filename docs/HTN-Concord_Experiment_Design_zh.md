## 0. 这是一项什么类型的研究

HTN-Concord **不是**模型对比研究，**也不是**预测模型研究。这一点必须说准确，因为分类错了就会套用错误的
报告规范和错误的统计方法。

本研究的形态是**以可计算参考标准为基准的诊断准确性型评估研究**：

| 角色 | 由谁承担 |
|---|---|
| 待评测试（index test） | LLM，接收任务输入，输出 `llm_output.schema.json` |
| 参考标准（reference standard） | 确定性指南引擎 `engine/evaluate.py`，编码 2025 AHA/ACC（DOI 10.1161/HYP.0000000000000249） |
| 分析单位 | 一个 case（`case_id`）= 一位患者档案在一个难度级别下的渲染 |
| 目标条件 | 成人原发性高血压的指南一致管理决策 |

引擎是**答案钥匙，不是竞争对手**。它在统计意义上没有自己的误差棒：它是对已发表指南的形式化，其正确性由
规则级单元测试和临床医生裁定（HC-49）建立，**不是**由与 LLM 的一致程度建立。任何"引擎表现优于 LLM"形式的
句子都是范畴错误，不得出现在论文中。

**这对"技术栈"问题的直接回答。** 部署技术栈（Next.js / FastAPI / LangGraph / pgvector / Postgres
checkpointer）里**不包含任何实验变量**。那些层是确定性管道：要么正确、要么有 bug，而 bug 是要修的缺陷，
不是要报告的发现。本设计只纳入以下会真正改变决策的层：输入表示、指南知识获取、数值计算、模型身份、
输出契约。

## 1. 研究问题

Master Plan 已经编号了三个研究问题。**本文档不重新编号**，只把它们细化到可检验的对比层面，并补充消融所能
支撑的子问题。

| RQ | 问题 | 对比 | 结论形态（示例，数字为占位符） |
|---|---|---|---|
| **RQ1** | 参考标准本身是否可复现、可辩护？ | 引擎 vs 临床医生裁定（HC-49）；引擎 vs 自身重跑 | "引擎跨次运行产生逐字节一致的标签；N 例裁定显示与独立临床评审 κ = _；M 处分歧判定为指南本身歧义，归入 `ABSTAIN`。" |
| **RQ2** | LLM 在决策链的哪一步、以何种机制偏离指南？ | 模型输出 vs 引擎标签，按 trace 步骤与失败模式分解 | "分期接近天花板（_%）；错误集中在风险分层与禁忌症识别；_% 的错误属于答案对但推理路径错。" |
| **RQ2a** | 多少误差来自"读"而非"推理"？ | C0（结构化）→ C1（vignette），同一模型 | "从结构化输入到渲染 vignette，一致率下降 _ 个百分点；该差值归因于信息抽取，而非临床推理。" |
| **RQ2b** | 难度是否如设计那样定位到抽取环节？ | C1 内部 simple → moderate → hard | "难度效应由 `extraction_f1` 承载，而在抽取正确条件下的 `decision_concordance` across levels 保持平坦。" |
| **RQ3** | 哪种干预修复哪一类错误？ | C1 → C2（检索）→ C3（工具）→ C3g（指南图谱） | "检索修复了指南过时类错误但不修复算术错误；PREVENT 工具修复了 _% 的风险计算错误，对知识类错误无效。" |
| **RQ4** | 合成 vignette 上的结论能否推广到真实临床文本？ | C1/C3（Task B）→ C4（Task C，MIMIC 出院小结） | 生态效度检验；大幅下降即界定了 vignette 结论的推广边界。 |

**RQ2 是现有医学 QA benchmark 做不到的贡献。** 它们只能报一个总分，因为它们没有参考推理路径。HTN-Concord
的引擎输出 `TraceStep` 和引文锚点，因此一次错误可以归因到具体**步骤**（分期/风险/禁忌症/药物类别选择）和
具体**机制**（抽取/推理/引文）——这正是 `trace_concordance` 与 HC-71 失败模式分类器所实现的。

## 2. 消融矩阵

**受控消融原则：相邻两个条件之间有且只有一个因素不同。** 所有条件共同冻结：case 语料及其划分、prompt 模板族、
输出 schema（`llm_output.schema.json` 的 SHA-256）、评估器及其指标定义、引擎 commit。**任何冻结产物一旦改动，
跨条件对比即失效**，必须全部条件重跑，而不是给某一个条件打补丁。

| 条件 | 输入 | 指南获取 | 计算 | 相对上一级的唯一差别 | 分离出的误差来源 | 构建状态 |
|---|---|---|---|---|---|---|
| **C0** | Task A —— 结构化 `PatientProfile` JSON | 仅参数化记忆 | 模型自行计算 | ——（基线） | 天花板：抽取完美时的推理能力 | ⬜ Task A = HC-52 |
| **C1** | Task B —— 渲染 vignette（simple/moderate/hard） | 仅参数化记忆 | 模型自行计算 | 输入表示 | **抽取**负担（C0−C1） | ✅ 语料已建（HC-50/HC-53）；⬜ 未跑 |
| **C2** | Task B | + 检索 2025 AHA/ACC 原文段落 | 模型自行计算 | 开启检索 | 被修复的**知识**缺口（C2−C1） | ⬜ 依赖 HC-44 锚点 |
| **C3** | Task B | + 检索 | + 确定性 PREVENT / 分期工具调用 | 开启工具 | 被修复的**计算**错误（C3−C2） | ⬜ 依赖 HC-61 工具调用适配 |
| **C3g** | Task B | + 指南**图谱**遍历 | + 工具 | 检索机制（扁平 RAG → 图谱） | 图谱的边际价值（RQ3 头条） | ⬜ Paper 2 / Phase 7 |
| **C4** | Task C —— MIMIC-IV 出院小结 | 同 C3 | 同 C3 | 输入来源（合成 → 真实 EHR 文本） | **生态效度** | ⬜ 依赖 HC-54 + MIMIC 队列 |

**交叉因素。** 每个条件都跨（a）≥1 个前沿模型与 ≥1 个开源权重模型（HC-61）、（b）Task B 的三个难度级别运行。
模型身份是交叉因素而非阶梯层级：**只有跨模型复现的失败模式才作为发现报告**。单模型的特异表现如实标注为
单模型现象，不进入机制性结论。

**这个阶梯要读"差值"，不要读"层级"。** 科学内容在 C0−C1、C2−C1、C3−C2、C3g−C3、C4−C3 这些差值里。绝对一致率
取决于语料难度，而语料难度是设计选择；共享同一语料的两个条件之间的差值则不受此影响。

**消融顺序的重要保留。** 该阶梯是累积式的，因此每个差值都是在**其前置条件的背景下**估计的，不等同于析因设计中的
主效应。若审稿人要求主效应（例如"有工具但无检索"），诚实的做法只有两种：扩展为析因设计（检索 × 工具 = 4 格），
或明确声明这一解释限度。**当前决定：以累积阶梯作为主分析，另在 Task B `moderate` 级别上补跑检索×工具的 2×2
格块作为次要分析** —— 既控制成本又回答交互问题。（待确认项，见 §9 D1。）

## 3. 结局指标

**主要结局。** `decision_concordance` —— 模型 `decision` 与引擎在隐藏行上给出的 `Decision` 精确匹配。

**并列主要安全结局。** `unsafe_recommendation` —— 对该患者构成禁忌的推荐（如妊娠合并 ACEi/ARB；高钾血症合并
升钾药物）。单独报告，**绝不并入一致率头条数字**。**⚠️ 在 NHANES 队列上不可估计 —— 见 §10 F2；该结局必须在
专门构建的禁忌症压力测试集上测量（HC-95）。****理由：错误类型不可互换。** 漏掉妊娠禁忌与过度保守地只建议
生活方式干预，在准确率指标里都只是"一个错误"，但临床上并不等价。引擎的禁忌症规则自动提供该严重度标签，
因此加权来自规则，而非事后主观判断。

**次要结局**（均在 Phase 6 定义，由 HC-70 实现）：`staging_correct`、`extraction_f1`、
`contraindication_recall`、`contraindication_false_positive`、`citation_support`、`trace_concordance`、
`abstention_appropriateness`。

**弃权（abstention）要计分，不能剔除。** 在决定因素确实未知时弃权的模型是行为正确的，应当据此计分；在可解答的
case 上为回避表态而弃权则应扣分。两个方向都报告（`abstention_appropriateness`），因为剔除弃权的 benchmark
实际上是在奖励瞎猜。

**报告粒度。** 所有结局按难度级别、按亚组（性别、年龄段、合并症）报告（HC-72）。亚组分析是**描述性且预先设定**的，
不具备显著性检验效能，将据此标注，不加显著性星号。

## 4. 统计分析计划

1. **配对，而非独立。** 每个 case 在每个条件下都出现，因此条件间对比是配对的。二元一致性的两条件对比用
   **McNemar 检验**，多条件阶梯用其推广形式；**绝不**使用两独立比例检验——那会高估方差并丢弃配对信息。
2. **聚类。** 一位患者贡献三个 case（三个难度级别），患者内部的 case 并不独立。采用**患者层面聚类**：
   聚类稳健标准误，或对所有头条数字采用**患者层面的 cluster bootstrap**（重抽样患者，而非 case）。
   数据划分本来就是患者层面的（`tasks/splits.py`），所以分析单位与划分单位一致。
3. **不确定性。** 每个头条指标报告 95% CI，按患者 bootstrap，B = 2000。
4. **模型随机性。** 当前前沿模型**无法钉住采样参数**（HC-64：`temperature`/`top_p`/`top_k` 被拒绝返回 400，
   且从来没有 `seed`）。因此每个 case 在每个条件下跑 **k = 5** 次，报告均值与重复间 SD，使运行间方差被**测量并
   可见**，而不是假装不存在。重复方差是一个要报告的量，不是要掩盖的麻烦。
5. **多重比较。** 阶梯会产生大量对比。预先指定主要对比（RQ2a 用 C0−C1；RQ3 用 C3−C2 与 C2−C1），在**每个 RQ
   family 内部**施加 Holm–Bonferroni 校正。其余对比一律标注为探索性。
6. **效应量优先于 p 值。** 以一致率差值（百分点）加 CI 作为主叙述，p 值居次。
7. **分析冻结。** 语料、prompt、schema、指标代码与本分析计划，在**第一次计分运行之前 git tag 冻结**。事后改动
   必须记入 changelog 并说明理由。这正是针对 LLM 论文最常见审稿质疑——"prompt 被调到数字好看为止"——的
   具体防御。

## 5. 可复现性表述（只说一次，但要说准）

有两个不同的主张常被混为一谈，论文中必须区分：

- **档案级可复现 —— 是。** 每个报告数字都能从存档 transcript 重新推导，无需任何网络调用。`runner.replay()`
  重新解析并校验存档原始文本，且**故意忽略**存档中的 `parsed` 块，因此被事后编辑过的 transcript 会失败而不是
  顺利往返。`ReplayProvider` 在 prompt 哈希改变时拒绝提供存档响应。
- **采样级可复现 —— 否，且无法做到。** 重新调用模型不保证返回相同文本，当前没有任何 API 参数能做到（HC-64）。
  这是服务提供方的属性，不是本框架的缺陷。

引擎那一半**是**确定性的、完全可复现的——这正是为什么在本研究中，参考标准是可复现的那个组件，尽管待评测试不是。

## 7. 效度威胁与局限（主动写出来，不要等审稿人发现）

1. **参考标准只是某一部指南的形式化。** 与 HTN-Concord 一致 ≠ 临床正确。指南沉默或含糊之处，引擎选择弃权而不是
   自创规则，这些 case 作为一个类别报告而不计分。计划中的 ESC 2024 对照模块（原则 6）**报告分歧而不合并分歧**。
2. **形式化本身是一种解释行为。** 规则由 Aria 手写；另一位同样称职的编码者可能在边缘处不同。临床医生裁定（HC-49）
   界定这一不确定性的范围，规则集公开发布使编码可被检验，而不是仅凭断言。
3. **Vignette 是合成的。** 由 NHANES 渲染的 vignette 比真实临床文本干净。C4（Task C，MIMIC 出院小结）正是为界定
   这一点而存在；在 C4 跑之前，仅基于 vignette 的结论必须明确表述为"仅限 vignette"。
4. **训练数据污染是无界的，而非仅仅是未受控的。** NHANES 是公开数据，2025 AHA/ACC 指南也是公开文本，二者都可能
   存在于模型预训练语料中。泄漏控制管的是**我们的语料构建**，管不了预训练。这限制了绝对分数的解释力，也是阶梯
   差值（污染同时影响两臂）承担主要论证责任的又一个理由。
5. **不具备采样级可复现性**（§5）—— 通过重复运行与 transcript **缓解**，而非解决。
6. **累积阶梯 ≠ 析因设计**（§2）—— 由计划中的 2×2 次要格块部分弥补，其余部分作为解释限度明确声明。
7. **亚组分析效能不足**，按描述性结果报告（§3）。
8. **单一临床领域。** 仅成人原发性高血压的启动与强化治疗。不对其他指南或其他专科作任何推断。
9. **NHANES 中 `clinical_cvd` 为空**，因此它只能作为"阳性触发"使用，队列中的高危组相对真实门诊人群被低估。

## 8. 预期用途声明（论文必需）

HTN-Concord 是**面向研究的测量工具**，不是临床决策支持系统。本设计中没有任何条件被部署，没有任何输出到达患者，
研究过程中也没有临床医生依据模型推荐采取行动。部署技术栈（Next.js / FastAPI / LangGraph / pgvector）属于
**后续**阶段，其评估将落入 DECIDE-AI 范畴并需要前瞻性、临床医生在环的研究设计——明确不在本研究范围内。

## 10. 语料可行性审计（2026-07-19 针对已构建的 Task B 语料执行）

上述设计已对照**实际存在的**语料（14,418 case / 4,806 患者，`benchmarks/task_b_manifest.json`）核查，
而不是对照它所假设的语料。**四项发现；其中第二项推翻了 §3 中的一个选择，已在此更正。**

**核实无误：** 数据划分是患者层面且互不相交（train 2,914 / dev 940 / test 952 位患者；train↔test 与
dev↔test 患者重叠均为 0）；泄漏审计在全部 14,418 个 case 上通过，禁用词命中 0、标签键命中 0；277 项测试通过，
其中包括 `test_every_level_carries_every_decision_relevant_value` —— 正是这项测试使得"逐级下降可读作抽取误差"
（RQ2b）成立。

**F1 —— 多数类占过半，没有基线的一致率头条数字无法解释。** 测试集多数类为 `lifestyle_only`，占 **51.5%**
（HC-96 重建后；重建前为 52.2%）。**一个无条件回答 `lifestyle_only` 的模型就能拿到 51.5%。****要求：** 每个一致率数字旁必须报告多数类基线，并优先以平衡准确率或
分类别召回作为头条指标。这不威胁阶梯差值（所有条件共享语料），但威胁任何绝对值主张。

**F2 —— `unsafe_recommendation` 在本语料上不可估计，因此不能按 §3 现有表述作为并列主要结局。**
4,806 位患者中只有 **9 位**携带任何禁忌症，且九位全部是高钾血症：**妊娠标记 0 例、血管性水肿标记 0 例。**
引擎的妊娠与血管性水肿规则从未被 NHANES 触发。测试集里阳性 case 只剩个位数——没有值得报告的 CI，
`contraindication_recall` 处境相同。**更正：** 该安全结局在**设计上**仍保留为并列主要结局，但必须在
**专门构建的禁忌症压力测试集**上估计，而不是在 NHANES 队列上。用大约 2 位测试患者报出一个安全率，
比不报更糟。已开 HC-95。

**F3 —— 妊娠标签污染的潜在风险。✅ 2026-07-19 已修复（HC-96）。**
`pipelines/nhanes/derive.py` 中已记录 `RIDEXPRG` 可获取但从未接入，导致**队列中 45 位孕妇携带空禁忌症列表**。
她们的 135 个 Task B case 标注为 `lifestyle_only`（129）、`at_goal_continue`（3）、`abstain`（3）——没有药物
治疗标签，但**仅仅**是因为该子群血压恰好偏低（收缩压 90–128）。一位血压达 stage-2 的孕妇本会**作为 ground
truth** 拿到 `initiate` 标签，而 HC-36 落地后该标签会指名 ACEi/ARB。

*修复方式。* 妊娠现在由 `RIDEXPRG` 派生（**只认阳性**："未询问/无法确定"绝不读作"未怀孕"），且引擎把它作为
**先于分期的范围闸门**——所编码的模块覆盖的是**非妊娠**成人的原发性高血压，因此孕妇档案无论血压如何都以
`pregnancy_management_out_of_scope` 弃权。范围判定刻意不依赖血压；否则语料的安全性仍然架在它的血压分布上。重建队列后
45 位全部弃权（已验证）。新增锚点 `HTN-CONCORD:abstain-out-of-scope`，与"数据不足"区分开：再多数据也不会
让所编码的规则变得适用。

*范围判断的来源 —— 2026-07-19 更正。* 本节早先的草稿声称"弃权"这个决定是在没有临床输入的情况下做出的。
**那是错的。** 它早已写在 Master Plan 的禁忌症规则表里（"妊娠期高血压管理超出范围，引擎应 ABSTAIN，
仅输出标记供评分"），也写在 HC-36 的 ticket 里，两者都出自 **2026-07-18 的心内科评审**。本次实现是**遵循既有
规范**，不是自创政策。HC-49 仍会确认它——正如它确认每一条规则——但这不是一个未经评审的判断。

*Ticket 来源。* 这项工作早已立票为 **HC-24**（P0，"接入 NHANES 妊娠标记"），出自同一次评审。HC-96 是审计
过程中重复立的票，已作为 HC-24 的重复项关闭。

**F4 —— 弃权样本稀薄且机制近乎单一；因 F3 的修复而部分改善。** HC-96 之前，全语料 92% 的弃权只有一个原因。
现在语料含三种机制——`stage1_risk_indeterminate`（393）、`pregnancy_management_out_of_scope`（135）、
`med_status_unknown`（36）——测试集有 117 个 abstain case。仍以单一原因为主，仍然不能写成关于"不确定性校准"
的一般性主张；应**按原因分别报告**而非合并，并在压力测试集（HC-95）中补充其他触发条件。

## 11. 执行顺序

试点（HC-80）只跑 **C1、moderate 级别、20 位患者 × 2 个模型**，其存在的目的是在 benchmark 缺乏区分度时尽早
终止（所有难度都接近天花板，或前沿模型 ≈ 开源模型处处相当）。**在试点证明语料能区分模型之前，C1 之后的任何
阶梯条件都不值得构建。** 试点之后：先冻结（§4.7），再跑 C0/C1 全量，随着门控 ticket 落地再跑 C2/C3，最后是
C3g 与 C4。
